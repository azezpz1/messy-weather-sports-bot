# Agent notes for this repo

Recommends NFL and Top 25 college football games worth watching for the weather.
Two bots publish to Bluesky, a collector saves forecasts, and a private dashboard
browses the history and manages collection schedules. This is a `uv`-managed Python
project. See [README.md](README.md) for setup and deployment.

## What this app is for

This is a **recommendation engine for messy games to watch, not a weather
report.** Each post tells followers "you should watch this game, because it's
going to be messy." That's the whole point of the app, and it should guide
every change to what gets posted:

- **Leave nice-weather games out.** Don't add them back for completeness, as
  context, or as a "not messy" section. A game appears only if it's messy
  (`GameWeather.is_messy`, with thresholds at the top of `messiness.py`).
- **Posting nothing is a valid outcome.** A day with no messy games gets no
  post and exits cleanly. Don't "fix" that by lowering thresholds or posting a
  fallback.
- **When tuning thresholds, err toward fewer, better recommendations.** The
  bar is "would a follower tune in for the weather?", not "is there any
  weather to mention?" A "Slight Chance Rain Showers" afternoon or a sunny
  15 mph breeze doesn't clear it. This was a real bug: on 2026-09-27 the bot
  posted a three-post thread of mostly sunny games.
- **Word posts as recommendations** ("Messy NFL games to watch"), never as a
  forecast or weather report.

## How the code is organized

Runtime modules live in `src/messy_weather_sports_bot/`. Start with the row for the
behavior you are changing. Test filenames are under `tests/unit/` unless a path is shown.

| Change | Start here | Tests |
| --- | --- | --- |
| Game eligibility and scoring | `espn.py` parses schedules, `venues.py` resolves stadiums, `weather.py` and `alerts.py` fetch NWS data, and `evaluation.py` and `messiness.py` evaluate it. | `test_messiness.py`, `test_weather.py`, `test_cfb_pipeline.py` |
| Game-day publishing | The `messy-weather-nfl-bot` and `messy-weather-cfb-bot` commands enter through `nfl.py` and `cfb.py`. `cli.py` handles arguments and Healthchecks, `pipeline.py` chooses the data source and publishes, and `state.py` stores thread progress. | `test_stored_publication.py`, `test_main.py`, `test_golden_dry_run.py` |
| Forecast collection and scheduling | `collector_cli.py` runs `messy-weather-collector`. `scheduler.py` claims jobs under the collector lock, `collector.py` gathers a rolling seven-day window, and `scheduler_store.py` and `collection.py` write SQLite history. | `test_scheduler.py`, `test_collector.py`, `test_collection.py` |
| Dashboard | `dashboard.py` runs `messy-weather-dashboard`. Pages read through `dashboard_read.py`. Task actions go through `scheduler_store.py` to update schedules or queue a refresh for the collector. | `test_dashboard.py`, `test_dashboard_read.py`, `tests/e2e/` |

Publishing first tries the latest independent collection for the sport and game day.
`stored_publication.py` requires a verified whole-day slate collected within 12 hours
with full forecast coverage and a successful alert lookup for each eligible outdoor
game. It applies the current scoring rules to saved forecast periods. The live path
runs when the snapshot is unusable or `--live` is passed. The dashboard displays
scores recorded at collection time. Its game list can retain the previous verified
slate when a schedule refresh fails.

Keep sport-specific rules in `Sport` (`sport.py`), including the game-day timezone,
venue catalog, and hooks like `game_filter`. `sports.py` registers the configurations
for shared tools. Tests share ESPN and NWS builders in `tests/support/` and fixtures in
`tests/unit/conftest.py`. The golden dry run pins the exact NFL post text.

The packaged `src/messy_weather_sports_bot/data/cfb_venues.json` is generated by
`scripts/generate_cfb_venues.py` (`venue_generation.py`, read back by `venue_table.py`).
Don't hand-edit it or its coordinates; make a correction in
`scripts/data/cfb_venue_overrides.json` with a `note` and rerun the generator. Its catalog
is looked up by ESPN venue ID only. `drift.py` reports unknown IDs.

College football covers only games with a Top 25 team (`cfb.ranked_only`), and the
"recommendation, not weather report" rules above apply to it unchanged: the header says
"Messy Top 25 college football games to watch", nice-weather games stay out, and a day with
no messy ranked game posts nothing. Never make it fall back to the NFL's credentials, state
file or healthcheck - it reads `CFB_`-prefixed variables only, so it can't post to the wrong
account - and give any new sport its own `env_prefix` and `state_key` (a test enforces it).

## Database changes

- Add a new Alembic revision under `src/messy_weather_sports_bot/migrations/versions/`
  for each shared SQLite schema change. Leave released revisions intact.
  See [Forecast history](README.md#forecast-history) for the Alembic commands.
- Keep upgrades transactional. Test both creating a fresh database and upgrading
  a populated database from the previous revision. Check that existing game and
  forecast observations survive the upgrade.
- Keep forecast persistence best-effort. Verify the bot can still publish if
  opening, upgrading, or writing the database fails. Dry runs can read saved forecasts
  but skip database writes, migrations, and publication state.

## Local checks

Run `./scripts/check.sh` before every push. Use `./scripts/check.sh -m "not integration"`
for lint, formatting, type checking, and tests without live ESPN and NWS requests.
Dashboard browser and proxy checks run in a separate CI job. See the
[dashboard test setup](README.md#private-forecast-dashboard) for Caddy and Playwright
prerequisites and run `uv run --locked --group e2e pytest --no-cov tests/e2e`.

For a manual preview, pass `--dry-run`. To avoid sending a Healthchecks ping from a
preview, clear `HEALTHCHECK_URL` and `CFB_HEALTHCHECK_URL` for that command. A dry run
can still fetch live ESPN and NWS data if it has no usable saved slate.

## Patterns that have bitten this repo before

Drawn from actual CodeRabbit/CodeQL findings and fixups in this repo's
history — check for these explicitly in anything you touch:

- **Shell/workflow injection**: GitHub Actions workflow steps that interpolate
  untrusted input (PR titles, branch names, tag names) directly into a `run:`
  shell command. Pass such values through `env:` and reference them as
  `"$VAR"`, never inline `${{ ... }}` in the script body.
- **Secrets leaking via process args**: don't pass tokens/credentials as CLI
  arguments to `curl` or other subprocesses (visible in process listings and
  often in logs) — use headers/env vars/stdin instead.
- **Unsanitized strings reaching logs, asserts, or ping bodies**: user- or
  API-controlled strings (error messages, alert text) have triggered
  CodeQL substring-sanitization findings more than once, including inside a
  *test* file after the production code was already fixed — the same unsafe
  pattern got reused. When you fix one occurrence, grep for the same pattern
  elsewhere (tests included) rather than assuming it's a one-off.
- **Timezone-naive datetimes**: NWS alert timestamps and similar external
  data have caused crashes when assumed to be timezone-aware; validate/reject
  rather than assume.
- **Release workflow checkout state**: `release-publish.yml` / the release
  scripts have previously broken on detached-HEAD checkouts and tag-ref
  parsing edge cases (e.g. `.git` suffix handling in repo names). If you
  touch release tooling, actually trace through what ref/HEAD state each
  step runs in rather than assuming `main` is checked out.
- **The release PR CI-approval gap is known and documented** in the README's
  "Releasing" section — don't rediscover it, and don't try to "fix" it by
  changing token permissions without reading that section first.

CodeRabbit reviews every PR (`.coderabbit.yaml`, `assertive` profile) — treat
its findings as a first pass to get ahead of, not a follow-up to react to.

## Branch hygiene

This repo has a lot of `Merge main into <branch>` commits in its history.
Before starting work, fetch and rebase/merge onto the current `main` rather
than working from a stale base — it avoids conflicts and means you're
testing against the code that will actually be there when the PR lands.
